## Multi-targeting

```xml
<TargetFrameworks>net10.0;net8.0</TargetFrameworks>
```

If `TargetFrameworks` (plural) is present, `TargetFramework` (singular) is ignored.

**Default recommendation: do not multi-target.** Since .NET 8 dies 2026-11-10, `net8.0;net10.0` buys a short compatibility window at the cost of `#if NET10_0_OR_GREATER` sprawl and a doubled test matrix. Single-target `net10.0` and move all consumers together.

Multi-target only when: the library is published to a public/partner feed; a `net472`/`netstandard2.0` consumer exists; or some apps genuinely cannot ship simultaneously.

If you do, remember multi-targeting also means `dotnet ef` needs `--framework` (see `references/05-efcore.md`) and re-triggers the package-pruning condition pattern:

```xml
<PackageReference Include="System.Text.Json" Version="8.0.5" Condition="'$(TargetFramework)' == 'net8.0'" />
```

## Nullable reference types on a legacy codebase

Four project-level values, and the order matters:

| Value | Meaning | Use when |
|---|---|---|
| `disable` | No annotations, no warnings | Stable library, rare changes |
| **`warnings`** | Flow-analysis warnings, no annotation semantics | **Phase 1 for a legacy codebase** — surfaces real NRE risk without changing the type system or the public contract |
| `annotations` | `?` honoured, warnings suppressed | Phase 1 for a *library* — stabilize the public contract before fixing internals |
| `enable` | Both | End state |

Rollout:

1. `<Nullable>warnings</Nullable>` repo-wide. Fix genuine null bugs. No API surface change, so no consumer churn.
2. Flip public-API assemblies to `annotations`; annotate every public member that can accept or return `null`. Consumers on `enable` benefit immediately.
3. Flip to `enable` and clear the residue.
4. Delete every migration-only `null!` / `default!` suppression and stray `#nullable` directive.

**Migrate leaf types first** (deepest in the dependency graph) so annotations propagate upward instead of fighting inference.

File-scoped opt-in during the transition:

```csharp
#nullable disable
public static class LegacyHelper { … }
#nullable restore
```

Generated code is auto-excluded when `.editorconfig` sets `generated_code = true`, the first comment contains `<auto-generated>`, or the filename ends `.designer.cs` / `.generated.cs` / `.g.cs`.

**.NET 10 raises the stakes:** `JsonSerializerOptions.Strict` and `RespectNullableAnnotations = true` make nullable annotations **load-bearing at runtime** for System.Text.Json. Getting them right is no longer cosmetic.

**If any project in the flip has EF Core entities, `enable` is also load-bearing for the database model — verify before shipping, not after.** EF Core's default conventions read C# nullable-reference-type annotations to decide whether a mapped property is `Required`. Every `string`/reference-type property that lacks `?` and lacks an explicit `.IsRequired(false)`/`[Required(false)]` override silently becomes "Required" in the EF model the moment `Nullable` flips to `enable` — regardless of what the real database column allows. On a legacy codebase where nullability was never audited, this is not a rare edge case; expect **dozens of properties** to flip at once, one per un-annotated reference-type column.

The failure mode is silent and comes in two shapes, worse than a compiler warning:
- If any of the affected entities use `HasData(...)` (seed data) and the seed omits a value for one of these now-"required" properties, `dotnet ef migrations add`/`has-pending-model-changes`/first-run model validation **throws outright** — not a warning, a hard crash, and it can happen at application startup (model building happens on first `DbContext` use), not just in design-time tooling.
- If a migration is generated against this drifted model without noticing, EF Core scaffolds `ALTER COLUMN ... NOT NULL DEFAULT ''`-style statements for every affected column — a **data-loss migration** that silently coerces every existing `NULL` in that column to an empty string if it's ever run against a real database with existing NULLs. This is a `dotnet ef migrations add` "may result in the loss of data" warning that is easy to skim past.

Do not skip this check because the earlier compile-and-warn gate passed — nullable warnings and EF model validity are two independent surfaces that both changed at once.

**Mandatory check immediately after any `enable` flip on a project with EF Core entities:**
1. `dotnet ef migrations has-pending-model-changes --project <p> --startup-project <sp>`. Clean output means no drift. A crash (not just "pending changes") means at least one seeded entity hit the required-property wall — fix that first before the check can even run cleanly.
2. Once it reports cleanly as "pending", run `dotnet ef migrations add ProbeNullableModelDrift --project <p> --startup-project <sp>` to see the actual scaffolded diff. **Read the `Up()` method.** If it contains `AlterColumn` calls flipping `nullable: true` → `nullable: false` with a `defaultValue`, that is the data-loss migration — do not apply it.
3. `dotnet ef migrations remove` to discard the probe migration.
4. For every property the probe surfaced, decide per-property against the actual DB reality (check the existing model snapshot / a `SELECT COUNT(*) WHERE column IS NULL` if a database is reachable): if the column has always been nullable and/or genuinely optional data, annotate the C# property `?` to match — this is a pure C#-side fix with zero SQL impact. Only use `.IsRequired()`/`[Required]` deliberately, for properties that should genuinely reject `NULL` going forward (that *is* a real schema change and needs its own reviewed migration, not a side effect of a language-level nullable flip).
5. Re-run step 1 to confirm clean, with no new migration file.
6. This applies to shared/base entity classes too (e.g. a generic lookup-table base class used by multiple derived entities) — one un-annotated property on a shared base can silently affect every table that uses it.

## ImplicitUsings, InternalsVisibleTo, AssemblyInfo

`<ImplicitUsings>enable</ImplicitUsings>` injects `System`, `System.Collections.Generic`, `System.IO`, `System.Linq`, `System.Net.Http`, `System.Threading`, `System.Threading.Tasks` and more. **Ambiguity risk on a legacy codebase:** a local type named `Task`, `Path`, or `File` now collides.

```xml
<ItemGroup>
  <Using Include="MyCompany.Common" />
  <Using Include="System.Threading.ExecutionContext" Alias="ExecutionContext" />
  <Using Remove="System.Net.Http" />
  <Using Include="System.Math" Static="true" />
</ItemGroup>
```

Prefer the MSBuild item over the hand-written attribute:

```xml
<ItemGroup>
  <InternalsVisibleTo Include="MyCompany.Shared.Tests" />
  <InternalsVisibleTo Include="MyCompany.Shared.Tests" Key="0024000004800000…" />  <!-- strong-named -->
</ItemGroup>
```

Delete the legacy `[assembly: InternalsVisibleTo("…")]` from `AssemblyInfo.cs` at the same time or you get **CS0579** duplicate-attribute errors. Delete legacy version/title attributes too — the SDK generates them (or set `<GenerateAssemblyInfo>false</GenerateAssemblyInfo>`).

## Source generators

Replace reflection with compile-time code. Meaningful for cold start, and required for trimming/AOT.

**System.Text.Json source generation**

```csharp
[JsonSourceGenerationOptions(
    PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase,
    ReferenceHandler = JsonKnownReferenceHandler.Preserve)]   // NEW in .NET 10
[JsonSerializable(typeof(OrderRequest))]
[JsonSerializable(typeof(OrderResult))]
internal partial class AppJsonContext : JsonSerializerContext;
```

Wire in: `options.TypeInfoResolverChain.Insert(0, AppJsonContext.Default);` (via `ConfigureHttpJsonOptions` in ASP.NET Core, `Configure<JsonSerializerOptions>` in a Functions worker).

**LoggerMessage source generator** — replaces interpolated `_logger.LogInformation($"…")`, which allocates and evaluates even when the level is disabled, and produces **no queryable properties** in Application Insights:

```csharp
internal static partial class Log
{
    [LoggerMessage(EventId = 1001, Level = LogLevel.Information,
                   Message = "Processed blob {BlobName} of {ByteCount} bytes")]
    public static partial void BlobProcessed(ILogger logger, string blobName, long byteCount);
}
```

**`[GeneratedRegex]`** — compile-time regex, no `RegexOptions.Compiled` startup cost, trim/AOT-safe. Replaces every `static readonly Regex` field. Requires the containing type to be `partial`:

```csharp
internal static partial class Patterns
{
    [GeneratedRegex(@"^\d{4}-\d{2}-\d{2}$", RegexOptions.CultureInvariant)]
    public static partial Regex IsoDate { get; }
}
```

**`[LibraryImport]`** — source-generated P/Invoke replacing `[DllImport]`, if the codebase has native interop.

## Trimming / AOT readiness

`PublishTrimmed` / `PublishAot` remain opt-in for normal apps in .NET 9 and 10 — no default changed. (File-based apps `dotnet run app.cs` are the exception: AOT by default on publish.)

Even without publishing AOT, turning the analyzers on documents reflection use and catches reflection-over-serialization bugs early:

```xml
<IsTrimmable>true</IsTrimmable>
<IsAotCompatible>true</IsAotCompatible>   <!-- implies trim, AOT, and single-file analyzers -->
```

Annotate the reflection you can't remove:

```csharp
[RequiresUnreferencedCode("Uses reflection over T's properties.")]
public static string Describe<T>() => …;

public static object Create([DynamicallyAccessedMembers(DynamicallyAccessedMemberTypes.PublicConstructors)] Type t)
    => Activator.CreateInstance(t)!;
```

.NET 10 changes to watch: **HTTP/3 disabled by default under `PublishTrimmed`**; **single-file apps no longer probe the executable directory for native libraries**; trim annotations removed from the `DefaultValueAttribute` ctor and trim-unsafe `Microsoft.Extensions.Configuration` paths (source-breaking if you relied on them).

.NET 9 feature switches make trimming tractable for libraries: `[FeatureSwitchDefinition("Feature.IsSupported")]` on a static bool property plus `<RuntimeHostConfigurationOption Include="Feature.IsSupported" Value="false" Trim="true" />`, and `[FeatureGuard(typeof(RequiresDynamicCodeAttribute))]` to suppress AOT warnings behind a guard.

## `TimeProvider` for testable time-dependent code

Ask during Modernization: **how many direct `DateTime.UtcNow`/`DateTime.Now` call sites exist, and are any of them in code that will ever need a unit test?** `grep -rn "DateTime.UtcNow\|DateTime.Now"` — on a legacy codebase this is often in the dozens, frequently including the audit-trail/timestamp mechanism used by every entity (e.g. a shared `SaveChanges()` override that stamps `CreatedOnDate`/`ModifiedOnDate`).

`TimeProvider` (abstract class, `System` namespace, built in since .NET 8 — no package) is the injectable replacement. Registering it is a **zero-risk, one-line, purely additive** step:

```csharp
services.AddSingleton(TimeProvider.System);
```

**Converting existing call sites is a completely different risk tier — do not bundle the two.** Registering `TimeProvider` in DI touches nothing existing and is always safe to do immediately. Actually converting `DateTime.UtcNow` → `_timeProvider.GetUtcNow()` at each call site is a real behavior-preserving refactor that needs verification, and on a codebase with no test coverage for the code being touched, there's no automated way to confirm nothing broke. Don't bulk-convert with find-replace across dozens of files in one pass.

If call-site conversion is in scope, sequence it as its own deliberate follow-up, one file at a time:
1. Inject `TimeProvider` via constructor.
2. Replace the call site.
3. **Write the test first (or immediately after), using `Microsoft.Extensions.Time.Testing`'s `FakeTimeProvider`** to actually assert the conversion changed something observable. A conversion with no accompanying test delivers zero testability benefit — it's just churn that happens to compile.
4. Gate per file, not batched — a mistake in file 1 shouldn't block or hide inside a 40-file diff.

Flag the highest-value, highest-risk candidates explicitly rather than converting them first: a shared audit-trail/timestamp mechanism used by every entity is exactly the kind of thing worth converting *eventually* for testability, but a mistake there is also the hardest to notice (silently wrong timestamps, not a crash) — sequence it after lower-stakes files have proven the pattern works.

## Test projects

### Framework support

| Framework | Package | net10.0 | Microsoft.Testing.Platform |
|---|---|---|---|
| xUnit v3 | `xunit.v3` (a **separate package line** from `xunit`) | ✅ | built in |
| MSTest | `MSTest` meta-package / `MSTest.Sdk` | ✅ | v3.2.0+ |
| NUnit | `NUnit` | ✅ | NUnit 5+ |
| TUnit | `TUnit` | ✅ | native |
| VSTest bridge | `Microsoft.NET.Test.Sdk` | ✅ | n/a |

Verify current versions on NuGet at upgrade time.

### Do this during the upgrade

**Option A — stay on VSTest.** Lowest risk. Bump the TFM, bump `Microsoft.NET.Test.Sdk`, no `global.json` `test` section. Nothing else changes.

```xml
<PropertyGroup>
  <TargetFramework>net10.0</TargetFramework>
  <IsPackable>false</IsPackable>
</PropertyGroup>
<ItemGroup>
  <PackageReference Include="Microsoft.NET.Test.Sdk" />
  <PackageReference Include="xunit.v3" />
  <PackageReference Include="xunit.runner.visualstudio" />
</ItemGroup>
```

**xUnit v1/v2 → v3 is its own migration**, not part of the TFM bump: test projects become executables (`<OutputType>Exe</OutputType>`), `IClassFixture`/`ICollectionFixture` semantics tighten, `Assert` gains overloads. Budget for it separately.

### Defer Microsoft.Testing.Platform

The .NET 10 SDK adds native MTP support to `dotnet test`, opted into via `global.json`:

```json
{ "test": { "runner": "Microsoft.Testing.Platform" } }
```

Consequences that break CI:

- **All-or-nothing per solution.** Every test project must use MTP; mixing VSTest and MTP projects is an error.
- **`dotnet test <path>` no longer works.** Use `--project`, `--solution`, or `--test-modules` (mutually exclusive).
- Remove the obsolete `TestingPlatformDotnetTestSupport` and `TestingPlatformShowTestsFailure` properties — the .NET 8/9 opt-in no longer works with MTP v2.

New capabilities once you do adopt it: `--max-parallel-test-modules`, `--coverage`, `--minimum-expected-tests <N>`, `--results-directory`, `--output Detailed`, and arg forwarding after `--`.

Per-framework enable properties (all require `<OutputType>Exe</OutputType>`): `EnableMSTestRunner`, `UseMicrosoftTestingPlatformRunner` (xUnit v3), `EnableNUnitRunner`.

MTP v1 → v2 renames, if you wrote custom extensions: `ITestApplicationLifecycleCallbacks` → `ITestHostApplicationLifetime`, `TestNodeFileArtifact` → `FileArtifactProperty`, `KeyValuePairStringProperty` → `TestMetadataProperty`, `IDataConsumer` moved namespace, `--diagnostic-output-fileprefix` → `--diagnostic-file-prefix`.

**Propose this as a follow-up, do not apply it inside the upgrade.**

### Tests that will need editing

- Integration tests built on `new WebHostBuilder()` / `TestServer` → `WebApplicationFactory<TProgram>` (`WebHostBuilder` is obsolete, `ASPDEPR004`). `Program.cs` must expose the entry point: append `public partial class Program { }` to top-level statements, or use `<InternalsVisibleTo>`.
- SQL snapshot/approval tests: EF 10 renames parameters `@__city_0` → `@city` and redacts inlined constants in logs.
- Split-query tests with non-unique `OrderBy` keys: results legitimately change (EF 10 fixed the ordering bug).
- SQLite-backed tests asserting on `DateTime`/`DateTimeOffset`: see the `Pre10TimeZoneHandling` switch in `references/05-efcore.md`.
- Anything asserting on Newtonsoft-shaped JSON in a Functions project that just moved to isolated.
- `WebApplicationFactory` + Playwright is now supported for Blazor E2E browser testing.

## Suggested order for this tier

1. Baseline: CPM + `Directory.Build.props`, `AnalysisLevel` pinned to `8.0` so the TFM bump is clean.
2. Class libraries → `net10.0`, single-target. Remove `System.Linq.Async`. Fix .NET 10 breaking changes. Green build **and** green tests before touching anything downstream.
3. Test projects → `net10.0`, VSTest mode. Defer MTP.
4. Post-upgrade hardening, each its own commit: raise `AnalysisLevel`, phase in `Nullable`, adopt source generators, then optionally MTP.
